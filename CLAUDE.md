# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

@AGENTS.md

ОВДП Портфель (repo `OVDPManager`, bundle ID and package `com.nero.mobile.dev.ovdpmanager`) is an Expo SDK 58 app (iOS and Android only, no web) for tracking Ukrainian government bonds (ОВДП), their future payments, investment plans and local backups. UI strings are hardcoded in Ukrainian (no i18n layer); code comments are in English. This file and `AGENTS.md` are the project's map — read the architecture and persistence rules before changing data flow or storage. `GLOSSARY.md` is the domain's language, written in plain Ukrainian for people new to ОВДП: each term as the UI shows it, the English name the code uses for it, and the words not to use instead. Take UI labels from it, and update it when a term is added or its meaning changes.

## Commands

The project uses Yarn 1 (`yarn.lock`) and pins Node `24.22.1` (`.tool-versions`; React Native Firebase 27 pulls `firebase@13`, which needs Node 24.12+); `yarn install` fails on another Node version. iOS builds need the Ruby/CocoaPods versions from `Gemfile` (`bundle install`).

```bash
yarn start                 # dev server (needs a development build; Expo Go cannot load Unistyles/MMKV)
yarn ios | yarn android    # bundle exec expo run:ios / expo run:android
yarn validate              # format:check + lint + typecheck + knip + test — Husky runs this before every push
yarn knip                  # dead code, unused exports and undeclared dependencies (knip.config.ts)
yarn test                  # Jest (jest-expo): the domain modules' tests
yarn format                # Prettier write
npx expo export --platform ios   # (or android) confirms the JS bundle builds
```

EAS builds iOS only, on a personal Expo account (`owner` / `extra.eas.projectId` in `app.json`). `eas.json` and the `publish:ios` script follow the same layout as the owner's other Expo apps: one profile, `production`, an App Store build for TestFlight internal testing with a remote, auto-incremented build number (`appVersionSource: remote`); no update channels, as there is no `expo-updates`. It extends `base`, which pins Node, Yarn and CocoaPods because EAS never reads the `Gemfile` — keep them in step with `.tool-versions`, `packageManager` and `Gemfile`. `yarn publish:ios` is the only EAS script (production build + auto-submit to TestFlight, `--no-wait`); anything else through `npx eas-cli`. Development builds are made locally (`yarn ios`), not on EAS. Releases go out through EAS Workflows: a push to `master` (a merged `develop` → `master` PR) runs `.eas/workflows/production.yml`, which builds the `production` profile and submits it to TestFlight on Expo's side, so the local EAS CLI login plays no part; its submit job never reads `eas.json`, so the workflow's `defaults.tools` repeats `base`'s Node and Yarn (keep them in step too); the GitHub repo is linked and the App Store Connect API key stored in the project on expo.dev. Put `[eas skip]` in a commit message to push to `master` without a build.

Before each commit Husky checks the branch name (`.validate-branch-namerc.json`) and runs ESLint and Prettier on staged files (`.lintstagedrc.json`), and commitlint checks the message (Conventional Commits). When committing without a user request to run checks, skip these hooks with `git commit --no-verify` to honor the user’s preference. `eslint.base.js`, `tsconfig.base.json`, `commitlint.config.js`, `.lintstagedrc.json`, `.validate-branch-namerc.json`, `.husky/*`, `.prettierrc.json`, `.editorconfig` and `.vscode/extensions.json` are the same in Local03, Tokomni, Oncall, OVDPManager and expo-linphone-module: change them in all five. The app's own rules go on top, in `eslint.config.js` (its aliases for `importOrder()`, its own rules) and `tsconfig.json` (`paths`, `types`).

Run `yarn validate` and other checks only when the user explicitly requests them; otherwise report that the changes are unchecked. Tests are Jest with the `jest-expo` preset (`jest` in `package.json`, `@/` mapped to `src/`): files named after the module they cover, `<module>.test.ts` (`backup.test.ts` for `backup.ts`), next to it (Jest's `testMatch` runs `src/**/*.test.ts`), exercising its interface with plain bonds and purchases, no React; a store's test is named after its folder (`plans.test.ts`, `operations.test.ts`, `bonds.test.ts`, `keyRate.test.ts`, `appSettings.test.ts`) and may import the store through its `index.ts`. `jest.setup.ts` loads Unistyles' mocks and stubs Nitro, which MMKV loads on import even though it mocks its own storage under Jest. Tests import modules by file or a store's index, so they never load the UI kit. Test domain calculations there; screens stay untested.

## Data validation

Follow the data validation boundaries in `AGENTS.md`: validate forms and decrypted backup contents before storing them, trust validated internal data, and type third-party API responses without runtime shape validation.

NBU `cptype` distinguishes ОВДП (`DCP`) from ОЗДП (`OZDP`); the bond's kind and currency are separate. Older cached bonds and backup snapshots have no kind and must remain unknown until NBU supplies it. Keep the optional kind in backup validation and compare market rates only for the same known kind and currency.

Coupon goals live on investment plans; `lib/coupon-goal/` estimates purchases and cash flow, and the flag FAB on the plan tab opens their form. Generated purchases carry `goalGenerated`; editing one makes it manual, and recalculation excludes only unconfirmed generated purchases when making a new copy. Backup v9 validates and preserves these fields and the selected purchase period; v6, v7 and v8 remain readable. See `spec/coupon-goal.md`.

The wallet's kind and currency filters live beside the operations they narrow, as `walletFilters` in `stores/operations/`. They are independent of the payment filters, persist between launches, and are controlled by the wallet header's filters modal.

The reports tab lists nine reports. Choosing one opens the report with default parameters; its header opens the filter screen, and applying it returns the selection as route parameters, without a filter store. In `screens/reports/`, `cash-flow/`, `fx/`, `portfolio/`, `position/` and `redemptions/` hold the related screens and calculations; `filters/` holds filter UI, and `shared/` holds the common report parameters, scope, charts and PDF. Cash-flow income allocates purchase cost to redemptions and FIFO sales. The currency report converts confirmed UAH events at the historical NBU rate, with remaining cost at the selected report-date rate; it is not a market valuation.

## Architecture

The default Expo layout, plus `stores/`, `api/` and `lib/` for what its template has no folder for:

- `src/app/` — routes only; `screens/` — screen bodies by area (`payments`, `holdings`, `plan`, `settings`, `backup`, `onboarding`), each with the parts, hooks and calculations only that area uses; `components/` — the UI kit, and `components/portfolio/` for the portfolio blocks several screens share (`WalletGate`, `BondsGate`, `ScheduleEventRow`…); `hooks/` — hooks over the stores and requests (`useWallet`, `useBonds`, `useKeyRate`, the purchase-form, bond-picker and backup hooks, `usePullToRefresh`, `useIsOnline`…); `stores/` — Zustand stores, a folder each; `api/` — the NBU client and requests (`api/nbu/`), the query client, backup files and Firebase (`api/backup/`); `lib/` — domain calculations and the backup codec (`lib/portfolio/`, `lib/add-purchase/`, `lib/payment-filters/`, `lib/backup/`); `utils/` — generic helpers (dates, formatting, numbers, storage, confirmations, navigation); `theme/`. The app icon, splash art and fonts are in `assets/` at the repo root.
- Modules are imported by file with the `@/` alias (`@/*` → `src/*`: `@/components/layout/Section`, `@/lib/portfolio/position`), or with `./` from the same folder. There are no barrel `index.ts` files except each store folder's. A screen area's own parts and calculations stay in its folder; what a second area needs moves to `components/`, `hooks/` or `lib/`. File names keep their kinds: `PascalCase.tsx` components, `camelCase.ts` modules, `use<Name>.hook.ts` hooks, `<name>.schema.ts` form schemas.

Routes in `src/app/` are thin and just render a screen component from `screens`; a screen opened over another (every route outside the tabs, `/onboarding` and `/welcome`) wraps it in `DeferredScreen` with its skeleton's shape, except the `formSheet` `/plan/actions`, which is sized to its content and renders at once, and `/intro`, the onboarding replayed from settings. A title the root layout shows while such a screen slides in comes from a function next to its screen (`purchaseScreenTitle`, `saleScreenTitle`, `planNameTitle`), which the screen uses too, never from a copy; the layout reads stores for it with getters (`getActiveOperations`), not hooks, so it does not re-render on every change.

- `index.ts` imports `src/theme/unistyles` (Unistyles configuration) before `expo-router/entry` — the theme must be registered before any `StyleSheet.create` runs.
- Screens: `payments` (one screen `/`, a year at a time: the year's totals, the monthly chart with the picked month spelled out, then only that month's events; filters modal `/payment-filters`), `holdings` (the wallet, the bond card, the bond picker `/add` with its filters modal `/bond-filters`, bond details `/add/[isin]` and the purchase form `/add/[isin]/purchase`, the sale screen `/bond/[isin]/sale`), `plan` (the active plan, «Мої плани» `/plan/list`, the plan-name screen `/plan/name` that is also `/welcome`), `settings` (backups, cloud account, theme, «Переглянути вступ» `/intro`), `backup` (create a copy `/backup/export`; restore `/backup/import` from the cloud, a file or pasted JSON), `onboarding` (`/onboarding`: a slide per part of the app with an `IconBadge`, «Далі» / «Пропустити»; shown once, before `/welcome`, through the root layout's `Stack.Protected`, until `completeOnboarding()`; `/intro` replays it). Adding a purchase, the payment filters and backups keep their logic in `lib/add-purchase/`, `lib/payment-filters/` and `lib/backup/`, their hooks in `hooks/` and their stores in `stores/`; their UI is in `screens/`.
- The portfolio is the domain: bond/purchase/plan types and calculations in `src/lib/portfolio/`, the stores `stores/operations/` and `stores/plans/`, the NBU (National Bank of Ukraine) catalog and key rate fetched in `api/nbu/` and cached in `stores/bonds/` and `stores/keyRate/`, and `useWallet()` (`hooks/useWallet.hook.ts`). Screens get positions, payments and purchase events from `useWallet()` rather than recomputing schedules. The Wallet itself is pure (`lib/portfolio/wallet.ts`): `buildWallet(operations, byIsin, today)` builds every field from the purchases, so they never drift apart; `useWallet()` is the adapter that feeds it the stores and the NBU data and adds the plan, the catalog and `refresh`. Calculations take a `Wallet`, which tests build from plain bonds and purchases (`lib/portfolio/wallet.test.ts`). The bond's dates follow one set of rules next to the `Bond` type: a bond is redeemed once its maturity date has passed (`isRedeemed`), on every screen alike, even while NBU has not published the redemption; it can be bought only before that date (`canBuyOn`: the picker, «Докупити» and the purchase form), so on the maturity day itself it is in circulation but no longer for sale; `maturesWithin` places it on a term scale (the picker's filter); `WalletGate` handles the empty-wallet / waiting-for-NBU states uniformly (it waits only while no operation has a saved bond, and not at all with `allowMissingBonds`, as the wallet does), `BondsGate` only waiting for NBU (bond picker, purchase form). Both read their state themselves; `StaleBondsNotice` also checks for cached data itself.
- Investment plans (`stores/plans/`) are the basis of the app. A plan is `{ id, name, isActive }`; its purchases — bought or planned, any date between issue and maturity — are the wallet purchases with its `planId`. There is no separate list of planned purchases. `useWallet()` gives the active plan's purchases (`isActive` in the plans store; falls back to the first plan), so the wallet and the payments show that plan. An operation is planned (`planned` on the operation) until the user confirms it took place, whatever its date: saved with a date ahead it starts planned (`plannedByDate`), and once that date has come it waits for confirmation (`awaitsConfirmation`: «Чекає підтвердження»); its purchase earns nothing received, and its sale counts as received, only once confirmed. The purchase and sale forms confirm it: saving with a date that has come («Купівля відбулась» / «Продаж відбувся», titled «Підтвердити купівлю» / «Підтвердити продаж») clears the flag, and «Купівля не відбулась» / «Продаж не відбувся» removes it (`useCancelPlanned`). A new plan becomes active (`createActivePlan`); screens add and remove purchases through `addOperationToActivePlan` / `removePositionFromActivePlan` without looking up the plan. Deleting a plan deletes its purchases. With no plans, the root `_layout.tsx` uses `Stack.Protected` to allow only `/welcome` and backup restore. A Position answers for itself (`lib/portfolio/position.ts`): `walletPosition(position, bond, today)` builds the Wallet's positions with their payments, state (planned, in circulation, redeemed, sold, unknown without NBU data), results (invested, coupons, redemption, received, expected, net income and return over the term, null while NBU has not published a redemption), «Річна дохідність» and what of it is still only planned (`planned`, its quantity and amount, which the wallet, the bond card and the bond picker show as «10 шт, з них 3 заплановано»); `resultsByCurrency` sums Positions up per currency: its net income and return over the term cover only the Positions whose redemption NBU has published, counting the others (`incompleteCount`) so a screen can say they are left out instead of hiding the result; `invested` covers every Position, those missing from the NBU data counted apart (`withoutDataCount`), as only their payments are unknown; and giving the sums it is worked out from (`published`; `netIncomeBasis` spells them out under «Чистий дохід» on the plans tab), and it averages their «Річна дохідність» by what they cost (the plan tab shows that average). The plans tab, the bond card, the purchase form (its draft is a Position of one purchase), and the wallet read these rather than computing their own; `lib/portfolio/position.test.ts` covers them. Purchases are added through one form (`/add/[isin]/purchase`: date, quantity, amount paid; price per bond = amount ÷ quantity, shown only); with `purchaseId` the same form edits that purchase (`updateOperation`), titled «Змінити купівлю», or «Підтвердити купівлю» while it awaits confirmation, opened from the bond card's purchase rows and «Найближчі купівлі». The form judges the purchase by its «Річна дохідність» (`assessPurchase` in `lib/add-purchase/purchaseHints.ts`, tested): against the key rate on its date for hryvnia bonds and against the coupon rates of bonds of its currency and term placed in the 12 months before (`newBondsRate`; both comparisons are `keyRateHint` / `newBondsHint` in `lib/portfolio/yieldHints.ts`, shared with the bond card); a loss or a yield over 3 points below the key rate is «Невигідна купівля». The price against the nominal and a long term are explained, never judged, as the yield already counts them. A yield no market gives (over 40 %, or beyond what `annualYield` computes) yields «Перевірте суму» instead of a comparison, and the purchase can still be saved.
- Payment filters (`lib/payment-filters/`, stored next to the operations they show, as `filters` in `stores/operations/`): currency (one at a time, as the chart has one money scale; a currency the wallet no longer has yields to the first one it has, which is the default), event types (coupons, redemptions, purchases, sales), time (all / upcoming — payments not yet received in full and operations not yet confirmed, whatever their date / past) and bonds; an empty type or bond list means all, and choosing every type resets to all. `effectiveFilters` fits the saved filters to the wallet's bonds and currencies (`walletScopeOptions` in `lib/portfolio/wallet.ts`): a missing currency yields to the first one, so a saved filter never hides everything; only the bonds of the currency shown are listed (`isinsIn`) and kept, here, the store keeping the others for when their currency is picked again. `filterSchedule(wallet, filters)` keeps the wallet's events of the currency, bonds, types and time picked (each event belongs to one bond, so the wallet is not rebuilt); the payments screen picks only the year and the month. The chart and the totals show only the types let through. On the same day a payment sorts before a purchase (`compareScheduleEvents`).
- The bond picker (`/add`) is narrowed by currency and term to maturity and sorted by maturity or rate, chosen in the «Фільтри ОВДП» modal with a count per option. The list and the modal share them through `useBondPicker`, whose logic is the pure, tested `bondPicker` (`lib/add-purchase/bondPicker.ts`). An explicitly chosen currency remains selected even when no bonds in it are in circulation. Search by ISIN, maturity date or coupon rate covers all bonds and ignores the filters.
- Navigation is native: the tab bar is `NativeTabs` (`expo-router/native-tabs`, the Liquid Glass bar on iOS 26, Material on Android). Native tabs draw no headers, so each tab is a group folder with its own stack (`(tabs)/(holdings)/_layout.tsx`, …), and screens pushed from a tab (bond, add, plan list) still open in the root stack over the tab bar. Every stack is `NativeStack` from `src/components/navigation/`, which owns the header options; don't set header colors per screen.
- Liquid Glass (`hasLiquidGlass` from `@/utils/glass`, iOS 26+): headers are transparent and the content scrolls under them, so scroll views keep `contentInsetAdjustmentBehavior="automatic"` and a non-scrolling element at the top is offset by `useHeaderHeight()`. Without glass (Android, older iOS) the header is a solid bar in `background`. Header buttons (`HeaderButton`) and the back button get glass from the system; the FAB is a tinted `GlassView` with a solid fallback. Glass belongs to the navigation layer and floating controls only, never to cards or other content.
- The payments tab is one year screen (upcoming payments are its «Майбутні» time filter). The bond card (`/bond/[isin]`) has a segmented control for payments and operations (purchases and sales; a sale's row opens it on the sale screen); the removal action is available on both sections.
- The bond card says whether to keep the bond or sell it today («Тримати чи продати», `holdOrSell` in `screens/holdings/holdOrSell.ts`, tested; it counts only confirmed operations, and says nothing for a bond only planned, on or after its maturity date or without its redemption published; a fully sold one says there is nothing left to decide). NBU publishes no market prices, so without one it compares the yield of the bonds held with the key rate and new bonds. The card shows only that verdict and its reasons; its header button (`SaleButton`) opens the sale screen `/bond/[isin]/sale` (`SaleScreen` → `SaleForm`, `useSaleForm`, `saleForm.schema.ts`), which records a sale: date, quantity and the net amount received, price per bond = amount ÷ quantity, shown only; with `operationId` it edits that sale, titled «Підтвердити продаж» while it awaits confirmation (`saleScreenTitle`). For a full sale dated today it also gives the two prices that decide («Ціни продажу», `SalePricesSection`): «Продаж без збитку» and «Вигідніше продати», above which the money from a sale earns more at the new bonds' rate (the key rate without them) than the bond does to maturity (`amountForYield`); and judges the entered price by «Дохідність від сьогодні», what that money earns in the bond, comparing the sale's result with holding (`SaleComparisonSection`). Both screens get it from `useHoldOrSell(isin, salePrice)`. Verdicts and their reasons are `Hint` / `Verdict` (`lib/portfolio/hints.ts`), shown by `HintsSection` here and in the purchase form.
- The plans tab shows the active plan: «Найближчі купівлі» (`upcomingPurchases(wallet)` in `screens/plan/upcomingPurchases.ts`, tested: the planned purchases to the end of next month per currency, those whose date has come and that wait for confirmation included, what the plan's payments bring in that time and the own money to have, a payment paying only for the purchases on or after its date; each row opens its purchase to confirm it or say it did not take place), then its totals; its header has the «Мої плани» button (`/plan/list`) to switch or create plans. Each plan's row there has a ⋮ button (`PlanRow`) that opens `/plan/actions` (`PlanActionsScreen`), a `formSheet` sized to its content with no cancel button, as a swipe down or a tap outside closes it: rename the plan, copy it with its purchases (`duplicateInvestmentPlan`, «… (копія)», the active plan stays) or delete it.

## Persistence rules

- State is Zustand `persist` over MMKV via the synchronous adapter in `src/utils/storage.ts`, so stores hydrate before the first render. Every store has the same layout: a folder in `src/stores/` named after it (`operations/`, `plans/` with the active plan's selectors and actions, `bonds/`, `keyRate/`, `appSettings/` with the theme, today, the seen onboarding and the toast) with `types.ts` (`<Name>State`), `store.ts` (`STORAGE_KEY`, exported `initialState`, and `use<Name>Store = create<<Name>State>()(persist(() => initialState, { name: STORAGE_KEY, storage: createJSONStorage(() => mmkvStorage) }))`; `appSettings` persists only the theme and the seen onboarding through `partialize`, as today is taken again on every launch and a toast does not outlive the session), `selectors.ts` (`use…` hooks and `get…` getters), `actions.ts` (exported functions with explicit return types that change the state through `setState`; no setters inside the state) and `index.ts` (`export * from './actions'; export * from './selectors'; export type * from './types';`, never the raw store hook; the app's only `index.ts` files). A screen's saved filters live in the store of the data they narrow, not in a store of their own: the payment filters are `filters` in `operations/`, the bond picker's are `filters` in `bonds/`, each with its own update and reset actions and a selector of just that field. Copy an existing store when adding one. The app is pre-release and installed on clean devices, so stores have no `version`/`migrate` and a changed shape simply starts empty, users moving data via backups; the one exception is `operations/` (persist `version: 2`, migrating the old `purchases` with `purchaseDate` from 0 and adding the `planned` flag from 1), and backups are written as v9 while v6, v7 and v8 are still imported.
- Storage keys are deliberately frozen: purchases live under `holdings-v1` (the state field is now `operations`), plans under `investment-plan-v1`, NBU cache under `nbu-bonds-v1`, NBU key rate under `nbu-key-rate-v1`, app settings (the theme and the seen onboarding) under `theme-preference-v1`. Don't rename them.
- No `__DEV__`-only code paths or dev fixtures in the app.
- Zod is used for forms and, as the one exception, for a backup's decrypted contents (`contentsSchema` in `lib/backup/contents.schema.ts`): a file can be broken or changed by hand, and restoring it replaces every plan and purchase. NBU responses and stored state are not validated: they are typed with TypeScript types and `as`/generics (`nbuClient.get<NbuSecurity[]>`, `JSON.parse(text) as T`). Don't add zod schemas or hand-written shape checks anywhere else.
- Every wallet purchase belongs to a plan (`planId`); the app shows the active plan's purchases, and with no plans only the first-plan screen (`/welcome`, the plan-name screen) and backup import are reachable. The bond picker `/add` adds purchases to the active plan.
- Backup JSON (`src/lib/backup/backup.ts`) is version 9 (with v6, v7 and v8 import support) and always encrypted with a key the user types (twice on export): Argon2id derives the key, AES-256-GCM encrypts `{ operations, plans, activePlanId?, theme? }` (`src/lib/backup/backupCipher.ts`, `react-native-quick-crypto`); the file keeps `format`, `version`, `exportedAt`, the `encryption` parameters and base64 `data`. `parseBackup(text, key)` reads v9, v8, v7 and v6: it checks `format` and `version`, decrypts (a wrong key throws `WrongBackupKeyError`), validates the contents with zod (`contentsSchema`, or `legacyContentsSchema` for v6 `holdings`, in `contents.schema.ts`), needs at least one plan and a plan in the file for every operation; it returns `BackupData`, which `serializeBackup(data, key)` also takes. `backup.ts` stays the file codec; file actions are in `src/api/backup/backupFile.ts`, and `restoreBackup` (`lib/backup/restoreBackup.ts`) reads the current plans and purchases, confirms if anything will be replaced and shows the toast. The key's form schema is `lib/backup/backupKey.schema.ts`. Restoring replaces all plans and purchases. A lost key cannot be recovered.
- The cloud copy is the same encrypted file, kept in Firebase: `@react-native-firebase/auth` signs in with Google through Firebase's web flow (`signInWithPopup` with `new OAuthProvider('google.com')`, as `new GoogleAuthProvider()` throws on the native SDKs; it returns by the plist's `REVERSED_CLIENT_ID` scheme, and closing it is `auth/popup-closed-by-user`), and Firestore `backups/{uid}` holds `{ email, exportedAt, backup }`, one copy per account, replaced on upload after a confirmation. Only `src/api/backup/` (`googleAccount.ts`, `cloudBackup.ts`) and `hooks/useCloudBackup.hook.ts` talk to Firebase; security rules live in `firestore.rules` and are pasted into the console. The RNFirebase 27 auth plugin patches SceneDelegate so Firebase reads that return link (`…/firebaseauth/link`); it does so whenever `expo-router` is a plugin. The link still reaches Expo Router, so `src/app/+native-intent.ts` drops it (`redirectSystemPath` returns `null`) instead of showing «Unmatched Route». Removing the cloud data has Google confirm the account (`reauthenticateWithPopup`), then deletes the document and the Firebase user. Without an internet connection (`useIsOnline` from `@/hooks/useIsOnline.hook`, over `expo-network`'s `useNetworkState`, unknown counting as online) the cloud parts — «Хмарна копія» in settings, «У хмарі» and «З хмари» on the backup screens — are not mounted: `OnlineOnly` (`src/components/layout/`) puts a line saying why in their place, and they come back with the connection.
- Server requests go through TanStack Query hooks (`useBonds`, `useKeyRate` in `src/hooks/`, their requests in `src/api/nbu/`): the hook fetches and saves each new answer into a persisted Zustand store in its `queryFn`, which the screens read. Stores never fetch. The catalog refetches when older than 6 hours (the current key rate 12), also when the app returns to the foreground; after a failure the next automatic try waits at least 5 minutes (`src/api/queryClient.ts`). The key rate is fetched a year at a time, never by date: one request takes every day of the year (NBU's `statdirectory/key` with `start`/`end`, weekends included), stored by year (`fillDailyRates` fills the days NBU skips); a past year is never refetched, the current one when older than 12 hours or a new day has begun. `useKeyRate(date)` gives `{ rate, failed }`: the rate on a date from its year (today's for a future date, the last saved day's for today before NBU publishes it, `keyRateOn`), and whether it is missing as its request failed, which the purchase form and «Тримати чи продати» then say (`keyRateFailedHint`); The query client and `QueryProvider` live in `src/api/`; a query with `meta.errorTitle` shows a toast with «Повторити» when it fails over data already shown. The cloud backup query (`useCloudBackup`) is the exception: it is read live and not cached in a store.
- Pull-to-refresh: give `RefreshControl` the state from `usePullToRefresh(refresh)` (`@/hooks/usePullToRefresh.hook`), never a background loading flag — otherwise the spinner shows whenever a screen opens and NBU data happens to refresh.
- Empty states: a screen or list with nothing to show renders `EmptyState` (`src/components/layout/`) with an icon, a title and a message saying why it is empty and what would show something (another year, other filters, the «Отримані» time…), never a bare line of text. `layout="screen"` (the default) fills a screen of its own; `layout="inline"` stands in a scrolling screen or a list (`ListEmptyComponent`) under what still shows there. When filters cause it, the icon is `funnel-outline` and the message points to them; it adds no button that repeats the header's filters button.
- Feedback: events go to a toast — `showToast({ tone, title, message?, action? })` from `@/stores/appSettings` (its `toast` field, never persisted; `ToastHost` rendered once in `src/app/_layout.tsx`; it shows for 4 s, 6 s with an action, closes on tap, and a new toast replaces the last). Use it for a failed NBU refresh over cached data (with «Повторити») and finished actions. Confirmations stay `confirmDestructive` alerts; lasting states (no NBU data) stay inline.
- Forms use `react-hook-form` with `zodResolver` and `mode: 'onChange'`. The zod schema turns input text into values (`z.input` / `z.output` typing on `useForm`) and holds the user-facing messages; a form schema that depends on data is a factory (`purchaseFormSchema(bond)` in `lib/add-purchase/`, shared with the sale form; `saleFormSchema` next to `useSaleForm`). Save is disabled while the form is invalid, and each field shows its error once edited: `FieldRow` (`src/components/form/`) under a row, or the `Section` footer under a block field. Read `isValid` / `errors` through `useFormState({ control })` and values through `useWatch` — not `form.formState`, which the React Compiler would cache.
- Screens with text fields scroll in `FormScrollView` (`src/components/layout/`, `KeyboardAwareScrollView` from `react-native-keyboard-controller` under the `KeyboardProvider` in `src/app/_layout.tsx`): it keeps the focused field and its error above the keyboard on iOS and Android. A screen whose content is a list that grows with the data is a `FlatList` / `SectionList` instead (the wallet, the bond picker, the payments, «Мої плани», the bond card): what comes before the rows goes in `ListHeaderComponent`, what ends the screen in `ListFooterComponent`, the empty state in `ListEmptyComponent`, each row in a `SectionCell` so a section's rows read as one card; the content is `[screenContent, { gap: 0 }]` and headers and footers space themselves, render callbacks are named functions above the return. Other screens use `ScreenScrollView`; filter screens stay there, as their rows are few and of many kinds.
- Dates are `YYYY-MM-DD` strings everywhere (as NBU returns them) and are compared as strings. Code that renders or queries reads today from `useToday()` (or `wallet.today`), never `todayISO()`, so a screen sees one today. `date-fns` is used only in `src/utils/date.ts`; put new date logic there, in local time.

## Styling conventions

- Every component has its own `StyleSheet.create((theme, rt) => …)` from `react-native-unistyles`; component states are `variants` + `styles.useVariants()`; safe-area insets come from `rt.insets`.
- No raw spacing, radius, shadow or color values in components: use `theme.space.*` (4-pt scale `xxs`…`xxxl`), `theme.radius.*`, `theme.shadowCard` / `theme.shadowRaised` and the palette (`src/theme/tokens.ts`, `palette.ts`). Static styles outside the theme (`screenContent`, FAB offsets) import `space` directly. Rows and screen edges are `lg` sideways and `md` vertically; sections are `xl` apart. Sizes of controls (heights, icon boxes) may stay numbers.
- Shadows use `boxShadow` strings, never `shadow*`/`elevation`. Never put a shadow and `overflow: 'hidden'` on the same view: the outer view casts it, an inner one clips (see `Section`, `SectionCell`). In dark mode `shadowCard` is transparent; the lighter card surface separates cards.
- Palette roles: deep teal `accent` for actions and income, vermilion `fab` / `danger` / purchases for money going out. Signed result amounts use `SignedValue`: `success` green above zero, `danger` red below zero, `primary` neutral at zero; gross amounts without a sign stay neutral. Status colors for advice: `success` (green, all well), `warning` (amber, look before acting), `danger` (a loss, a mistake, an error); `*Surface` tints a banner of that status. Errors that block an action stay `danger`; a state that only needs attention (stale or missing NBU data) is `warning`. Text pairs pass WCAG AA; chart series were checked with the dataviz validator — re-run it when changing `series*` colors.
- Colors needed as non-style props (`tintColor`, `placeholderTextColor`) go through `withUnistyles`. `useUnistyles()` is reserved for navigator options in `src/app/`.
- The theme is chosen in settings: `src/stores/appSettings/` stores it and `src/theme/themePreference.ts` applies it to Unistyles (`adaptiveThemes` for system, `setTheme` for an explicit one) and to `Appearance`, so native controls match; `unistyles.ts` reads the stored choice before `StyleSheet.configure`.
- `DateField` (`src/components/form/`) gets `themeVariant` and `accentColor` through `withUnistyles` on iOS. On Android the dialog takes its colors from the native theme added by the local plugin `plugins/withDatePickerAccent.js`: its `app.json` parameters repeat the palette's `accent` and header colors, so update them with `palette.ts` and rebuild.
- Icons are Ionicons from `@react-native-vector-icons/ionicons/static` (font embedded by its config plugin in `app.json`; not `@expo/vector-icons`, which Expo is deprecating). In components use `ThemedIcon` from `src/components/icon/` with `uniProps={(theme) => ({ color: … })}`; icon props are typed `IconName`. Tab bar icons are the exception: SF Symbols (`sf`) on iOS and Material Symbols (`md`) on Android in `NativeTabs.Trigger.Icon`, the SF Symbol filled when the tab is selected.
- Illustrations are drawn with React Native Skia (`@shopify/react-native-skia`): `IconBadge` (`src/components/icon/`, an Ionicons glyph on a lit disc in a breathing glow with a comet on its orbit; `EmptyState` takes its `icon`) and the onboarding backdrop (blurred patches of `accent` and the series colors that drift and follow the pager). Skia takes colors as props, so the drawing component gets them through `withUnistyles` + `uniProps`; motion runs off `useClock()` with Reanimated derived values and stands still under reduced motion. `withAlpha` (`@/utils/color`) fades a palette color for gradients. The shared `ColumnChart` draws its plots with Skia while native text keeps axes and labels accessible. `ColumnChart` uses stacked series and a signed baseline.
- Waiting on the network shows a skeleton, never a spinner (`src/components/skeleton/`): `SkeletonBlock` bars and circles in `muted` with a band of light (`raised`) drawn by Skia, inside a `SkeletonGroup` that gives them one `useClock()` and one origin, so a single band sweeps across them all; it is announced by its `label` and stands still under reduced motion. `LoadingState` is a screen's skeleton (`SkeletonCard` over a section of rows, behind `BondsGate` / `WalletGate`), `BondsUnavailableCard` a `SkeletonCard`, the cloud copy's date a `SkeletonBlock`. Every screen opened over another slides in as a skeleton too: its route wraps it in `DeferredScreen` (`src/components/navigation/`) with a `ScreenSkeleton` shape (`list`, `form`, `filters`), and the screen itself, its hooks and its header buttons included, mounts on the stack's `transitionEnd` and fades in. The push starts as soon as the skeleton is drawn, so a screen's work never holds the transition back. The first screen of a stack (the tabs, `/onboarding`, `/welcome`) has no transition and renders at once.
- Each currency has its own badge color (`currencyUah` berry, `currencyUsd` green, `currencyEur` indigo; `currencyColor(currency)` from `@/theme/currency`), used by the `Avatar` of the wallet's and the bond picker's rows; rows of a purchase or a payment (the schedule, the bond card's purchases) badge it with `Avatar` in the event type's series `badge` color. A row that leads with such a badge takes `Avatar`, never a copy of it. `Avatar` takes any palette key that `accentText` reads on: the light label sits on these fills, on `accentFill` (the primary button, the selected segment) in both themes, each at 4.5:1 or more. The currencies were checked with the dataviz validator in both themes — re-run it when changing them.
- Chart series colors use `SeriesColor` keys (`coupon`, `redemption`, `sale`, `purchase`, `plannedPurchase`) from `src/theme/series.ts`, not color strings. Charts over time split purchases into those made (`purchase`) and planned ones (`plannedPurchase`, plum, «Заплановані купівлі»): the payments chart. A planned purchase's rows keep the purchase's badge and text colors.
- One React component per `.tsx` file; shared types/utilities go in separate `.ts` files next to their consumers.
- `src/components/` is the app's UI kit; screens are put together from it, and a pattern that repeats across screens becomes a kit component rather than a copy. Build from these before writing a layout of your own:
  - `Section` is a titled card of rows: it puts a `Separator` between each two rows itself, opening fragments, maps and conditions, so callers never add one. `Card` is a padded card of free content (figures, charts, legends); both take `title` and `footer` (`SectionFrame`), so no screen wraps a `SectionTitle` and a card in a view of its own. Inside a `Card`, parts are split by `<Separator variant="card" />` (`table` between table rows).
  - `ListRow` is every list row: `leading` (an `Avatar`), `title` / `subtitle` (strings take the standard text, nodes their own), `children`, `trailing`; with `onPress` it is pressable with the shared pressed state. `LinkRow`, `CheckRow` and `ActionRow` are built on it, and so are the wallet's, the picker's, the schedule's and the purchases' rows.
  - `InfoRow` wraps its `value` in the row's text style, so a value is text: a string or text components such as `Percent`; `loadingLabel` puts a skeleton bar in its place while the value loads.
  - Amounts of money are shown by `Money` (`«10 200,50 ₴»`, `null` → «—»), the same way: inside a `Typography` or as the value of `InfoRow`, `LegendRow` or `TotalRow`; an amount inside a string is `formatMoney`. A signed amount in an `InfoRow` takes `signedValue`, not a `SignedValue` of its own.
  - Percentages are shown by `Percent` (`«16,5%»`, `null` → «—»), which takes the style of the text around it; a percentage inside a string (a subtitle, an accessibility label, a hint) is `formatPercent`. Never write `${value}%`.
  - `OnlineOnly` shows what needs the internet only while the device is online, a `warning` line with its `offlineMessage` in its place otherwise.
  - `SegmentedSection` is a filter section of one choice out of a few; `ResetFiltersHeader` is a filters screen's header with its reset button; `ShareBar` takes a `caption` for the share in words under it.
  - The chart's stacking and its words for screen readers live in `chart/columnStacks.ts` (tested).
- A component stays under 300 lines; past that, its pure calculations move to a `.ts` file next to it (with tests) and repeated parts to components of their own.

## Operation history and saved bonds

The persisted portfolio is `PlanOperation[]`: `id`, `planId`, `type: 'purchase' | 'sale'`, `isin`, `date`, `quantity`, `amount`, `currency`, `planned` (not yet confirmed), and `ovdp` (the complete Bond including payments). Amounts are the full debit including fees or net sale proceeds. Only migrated purchases with lost data may have `ovdp: null`. `stores/operations` retains the `holdings-v1` key with persist version 2: from 0 it migrates the old `purchases` (with `purchaseDate`) into operations, taking each bond from the cached catalog (`migratePurchases`); from 1 it adds `planned` (`withPlannedFlags`: kept if set, else dated after today), so past operations stay made and nothing dated ahead is confirmed. Active-plan selectors and actions belong to `stores/plans`; there is no activePlan folder.

`buildWallet` resolves embedded bonds before the catalog fallback. Snapshot synchronization retains missing ISINs and payment rows, preserves past payment amounts, and updates future matching rows; it applies the same result to every operation of that ISIN. A cached catalog only recovers missing snapshots (ISINs with no saved bond): when restoring a backup, and in `saveBonds` before a new NBU answer replaces it. The latest server answer may update future data. Fully sold positions remain in history. Sales reduce entitlement only after the sale date (the seller keeps that day's coupon); FIFO allocates sale proceeds to purchases for annual yield. History validation rejects overselling, including after editing/deleting purchases. The sale form records dates (a sale dated ahead is planned until confirmed), quantities and full net amounts; comparisons remain available for a full sale today. History validation counts planned operations too, as the plan is one scenario. Payments are still computed from schedules, not confirmed bank receipts.

Backup v9 includes purchase periods, coupon goals, generated-purchase markers, and operations with their `planned` flag and snapshots; a file without the flag restores through `withPlannedFlags`, and v6 purchases are flagged by date. The decoder still accepts encrypted v6 holdings, using the original version in the encryption AAD, and validates decrypted contents before replacing stores. File backups and portfolio calculations do not require NBU. Cloud backups still use the existing single Firestore document and its size limit.
