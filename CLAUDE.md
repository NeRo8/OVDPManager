# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

@AGENTS.md

ОВДП Портфель (repo `OVDPManager`, bundle ID and package `com.nero.mobile.dev.ovdpmanager`) is an Expo SDK 58 app (iOS and Android only, no web) for tracking Ukrainian government bonds (ОВДП), their future payments, investment plans and local backups. UI strings are hardcoded in Ukrainian (no i18n layer); code comments are in English. This file and `AGENTS.md` are the project's map — read the architecture and persistence rules before changing data flow or storage. `GLOSSARY.md` is the domain's language: each term with the Ukrainian word the UI shows for it. Take UI labels from it, and update it when a term is added or its meaning changes.

## Commands

The project uses Yarn 1 (`yarn.lock`) and pins Node `24.22.1` (`.node-version`; React Native Firebase 27 pulls `firebase@13`, which needs Node 24.12+); `yarn install` fails on another Node version. iOS builds need the Ruby/CocoaPods versions from `Gemfile` (`bundle install`).

```bash
yarn start                 # dev server (needs a development build; Expo Go cannot load Unistyles/MMKV)
yarn ios | yarn android    # expo run:ios / run:android
yarn validate              # format:check + lint + lint:fsd + typecheck + test — Husky runs this on every commit
yarn test                  # Jest (jest-expo): the domain modules' tests
yarn lint:fsd              # Steiger: FSD layer/slice boundary checks
yarn format                # Prettier write
npx expo export --platform ios   # (or android) confirms the JS bundle builds
```

EAS builds iOS only, on a personal Expo account (`owner` / `extra.eas.projectId` in `app.json`). `eas.json` and the `build:*` scripts follow the same layout as the owner's other Expo apps: `development` is an `expo-dev-client` build for registered devices (`distribution: internal`), `production` an App Store build for TestFlight internal testing with a remote, auto-incremented build number (`appVersionSource: remote`); no update channels, as there is no `expo-updates`. Both profiles extend `base`, which pins Node, Yarn and CocoaPods because EAS never reads the `Gemfile` — keep them in step with `.node-version`, `packageManager` and `Gemfile`. Scripts: `yarn build:dev:ios`, `build:ios`, `build:ios:submit` (TestFlight, `--no-wait`), `build:local:ios`; anything else through `npx eas-cli`.

"Done" means `yarn validate` passes, tests included. Tests are Jest with the `jest-expo` preset (`jest` in `package.json`, `@/` mapped to `src/`): files named `*-test.ts` in a `__tests__` folder next to the module they cover, exercising its interface with plain bonds and purchases, no React. `jest.setup.ts` loads Unistyles' mocks and stubs Nitro, which MMKV loads on import even though it mocks its own storage under Jest; `@/shared/ui` is an empty module under Jest (`jest.sharedUiStub.ts`), as slices' public APIs also give their screens' parts and the tests render nothing. Test domain calculations there; screens stay untested.

## Architecture

Feature-Sliced Design, imports only point down: `app` (routes in `src/app/`) → `pages` → `features` → `entities` → `shared`. Cross-slice imports go through each slice's `index.ts` using the `@/` alias (`@/*` → `src/*`); imports inside a slice are relative. Routes in `src/app/` are thin and just render a screen component from `pages`.

- `index.ts` imports `src/shared/theme` (Unistyles configuration) before `expo-router/entry` — the theme must be registered before any `StyleSheet.create` runs.
- Pages: `payments` (one screen `/`, a year at a time: the year's totals, the monthly chart with the picked month spelled out, then only that month's events; filters modal `/payment-filters`), `holdings` (the wallet, the bond card, the bond picker `/add` with its filters modal `/bond-filters`, bond details `/add/[isin]` and the purchase form `/add/[isin]/purchase`), `reports` (the «Звіти» tab, between the wallet and the plan: a list of reports, each with a short description, each opening its own screen under `/reports/…` (year, fx, period, year-over-year, redemptions, portfolio, structure, yield, bond); reports are what will later be exported as PDF, so a report shows everything at once, with no taps to reveal parts (filters only choose what it covers), and ends with the plan and the date it was made. The year and period reports share one model, `periodReport(wallet, from, to)` (`model/periodReport.ts`; the year report is the period from 1 January to 31 December, `model/yearReport.ts`), and the same blocks (`Report*` in `ui/`), which take their wording from `model/reportTerms.ts` («Сальдо року» / «Сальдо періоду»…). Every report but the list takes what it covers from one filters modal, `/report-filters/[report]` (`ReportFiltersScreen`: the report's own section, then «Валюта» and «ОВДП» for all but the bond report), opened by a header button that is filled while a filter is on (`ReportFiltersButton`); the year and period reports state the year or the dates at their top (`ReportHeading`). The filters live in `features/report-filters/`: one store, `reportFilters`, keeps every report's saved filters by its name (`ReportName`), and `fitReportFilters(report, saved, wallet)` fits them to the wallet, giving the report's filters as its screen uses them (the year shown, the period's dates, the bond and its choices), the wallet narrowed to their currency and bonds and how many filters are on; a saved year, bond or currency the wallet no longer has gives way to the default. Screens get all of it from `useReport(report)` (`pages/reports/model/`), and never narrow the wallet themselves; the currency and bonds sections (`ReportScopeSections`) are shared. The year report picks a year from the plan's first purchase to its last payment (`reportYears`; none saved means this year, or the nearest the plan has, so picking that one saves none). The period report picks this or last month or quarter, whole; the year to date or the last 12 months, the default, up to today; the whole plan (`walletSpan`); or «Власний період», the only one whose two dates are set by hand, shown only when it is chosen and starting from the dates shown before; its table by month adds a row with the year when the months span several. Each currency of the active plan gets its sums, the bonds that stand out (highest and lowest «Річна дохідність», the largest «Дохід за рік»; a bond's yield is its purchases' yields, as the purchase form computes them, weighted by amount), a chart of monthly cash flows (yearly for periods longer than 12 months), a table by month and each bond's sums, income, yield and share of the year's income; «Сальдо року» is the payments less the purchases, «Дохід за рік» the coupons plus what redemptions brought over the cost of the bonds repaid. The year-over-year report (`model/yearOverYearReport.ts`) sets the plan's years side by side in each currency, from its first purchase or payment to its last, empty years included: the sums of all of them (`ReportSummary`), the years with the largest income, payments and purchases, a chart of each year's payments over its purchases (`ColumnChart` from `shared/ui/chart`, the payments screen's chart with any columns and no selection) and bars of each year's income, then a table of each year's purchases, coupons and redemptions and one of its «Сальдо», «Дохід» and the income's change against the year before; its filters hold only the currency and the bonds. The redemptions report (`model/redemptionsReport.ts`) shows the plan's redemptions still ahead at first, or those received, or all (its filters add the currency and the bonds): per currency the sum, received and expected, the nearest and the last redemption, a `ColumnChart` by year, a table by year and quarter with each one's share, and every redemption, as rows of its list. The portfolio report (`model/portfolioReport.ts`) lists the wallet's bonds held to maturity, all at first, or those in circulation (planned ones included), or those redeemed (its filters add the currency and the bonds): per currency the sums as the plan tab makes them (`resultsByCurrency`; bonds missing from the NBU data are listed but left out of them), a horizontal chart of the largest investments, then a row for each bond by maturity with where it stands, its rate, quantity and «Річна дохідність», what it cost and pays, its «Чистий дохід» and its share of what the currency's bonds cost. The structure report (`model/structureReport.ts`) splits the money in the wallet's bonds still in circulation, what their purchases cost (planned ones too, or only those made), side by side by currency with no shares across them, as there is no exchange rate, then in each currency the average time to maturity and coupon rate weighted by amount, a horizontal chart and the split by time left to maturity (to 6 months, 6–12 months, 1–2, 2–3, over 3 years) and a row for each bond, the largest share first. The yield report (`model/yieldReport.ts`) shows the «Річна дохідність» of the wallet's bonds, those still in circulation at first, or all, or the redeemed (`BondStatusSection` and `BondStatusEmpty`, shared with the portfolio report): per currency the average weighted by what the bonds cost, the average coupon rate, and for hryvnia bonds the NBU key rate today, the gap in percentage points and both as bars; a horizontal chart of known annual yields, then a row for each bond, the highest yield first, with the key rate on its purchase dates for hryvnia bonds. The key rate is the hryvnia's, so other currencies' bonds are not compared with it. The bond report (`model/bondReport.ts`) is about one bond of the wallet, picked in its filters (none saved means the one nearest to maturity): the issue's terms, what it cost, pays and earns, its «Річна дохідність» next to the key rate on its purchase dates for a hryvnia bond, its money by year (`YearsMoneyChart`), then its purchases and payments as rows. Report tables are `ReportTable` (`ui/reportCells.ts` formats their cells); a bond's state reads the same in every report (`bondStateLabel`).), `plan` (the active plan, «Мої плани» `/plan/list`, the plan-name screen that is also `/welcome`), `settings` (backups, cloud account, theme), `backup` (restore from a file or pasted JSON), `onboarding` (`/onboarding`: a slide per part of the app with an `IconBadge`, «Далі» / «Пропустити»; shown once, before `/welcome`, through the root layout's `Stack.Protected`, until `completeOnboarding()`). Features: `add-purchase`, `backup`, `onboarding`, `payment-filters`, `report-filters`, plus planning; their UI lives in pages.
- The FX report (`/reports/fx`) covers past UAH bond purchases and payments in the active plan. It shows all time by default or one calendar year; all time includes every past purchase, even bonds with no event in an intervening year. Each cash flow is converted to USD or EUR at the official NBU rate for its date. Daily rates come from the NBU range API and are cached by currency and year in `entities/portfolio/api/exchangeRate/`. The selected-year chart compares cumulative purchases at their own rates with remaining UAH purchase cost at each month's rate plus payouts at their payment-date rates. The all-time chart plots the monthly difference between those two sums against zero, with a table of cash flows by year. This is not a market price or cash currently available: reinvested payments remain among payouts and their new purchases count again as purchases. The snapshot separates received payouts from remaining cost and compares their sum with all purchases. The period's balance is cash flow; cumulative gain or loss is shown only for bonds fully redeemed by the report date. Filters choose all time or one year, comparison currency and UAH ISINs.
- `src/entities/portfolio/` is the single domain entity: bond/purchase/plan types and calculations, the persisted stores, the NBU (National Bank of Ukraine) catalog fetch + cache (`api/`), and `useWallet()`. Screens get positions, payments and purchase events from `useWallet()` rather than recomputing schedules. The Wallet itself is pure (`model/wallet.ts`): `buildWallet(purchases, byIsin, today)` builds every field from the purchases, and `narrowWallet(wallet, { currency, isins })` builds a Wallet of only the purchases kept, so its fields never drift apart; `useWallet()` is the adapter that feeds it the stores and the NBU data and adds the plan, the catalog and `refresh` (`ActiveWallet`). Calculations take a `Wallet`, which tests build from plain bonds and purchases (`model/__tests__/wallet-test.ts`). The bond's dates follow one set of rules next to the `Bond` type: a bond is redeemed once its maturity date has passed (`isRedeemed`), on every screen alike, even while NBU has not published the redemption; it can be bought only before that date (`canBuyOn`: the picker, «Докупити» and the purchase form), so on the maturity day itself it is in circulation but no longer for sale; `maturesWithin` places it on a term scale (the picker's filter, the structure report); `WalletGate` handles the empty-wallet / waiting-for-NBU states uniformly, `BondsGate` only waiting for NBU (bond picker, purchase form). Both read their state themselves and take only `children`; `StaleBondsNotice` also checks for cached data itself.
- Investment plans (`model/plans/`) are the basis of the app. A plan is `{ id, name }`; its purchases — bought or planned, any date between issue and maturity — are the wallet purchases with its `planId`. There is no separate list of planned purchases. `useWallet()` gives the active plan's purchases (`model/activePlan/`, kept across launches; falls back to the first plan), so the wallet and the payments show that plan, and a future purchase earns only after its date (marked «заплановано» in the wallet). A new plan becomes active (`createActivePlan`); screens add and remove purchases through `addPurchaseToActivePlan` / `removePositionFromActivePlan` without looking up the plan. Deleting a plan deletes its purchases. With no plans, the root `_layout.tsx` uses `Stack.Protected` to allow only `/welcome` and backup restore. A Position answers for itself (`model/position.ts`): `walletPosition(position, bond, today)` builds the Wallet's positions with their payments, state (planned, in circulation, redeemed, unknown without NBU data), results (invested, coupons, redemption, received, expected, net income and return over the term, null while NBU has not published a redemption) and «Річна дохідність»; `positionIncome` gives a Position's «Дохід» over a span and `resultsByCurrency` sums Positions up per currency: its net income and return over the term cover only the Positions whose redemption NBU has published, counting the others (`incompleteCount`) so a screen can say they are left out instead of hiding the result, and it averages their «Річна дохідність» by what they cost (the plan tab and the yield report show that average). The plans tab, the bond card, the purchase form (its draft is a Position of one purchase), the wallet and every report read these rather than computing their own; `model/__tests__/position-test.ts` covers them. Purchases are added through one form (`/add/[isin]/purchase`: date, quantity, amount paid; price per bond = amount ÷ quantity, shown only).
- Payment filters (`features/payment-filters/`): currency (one at a time, as the chart has one money scale; a currency the wallet no longer has yields to the first one it has, which is the default), event types (coupons, redemptions, purchases), time (all / upcoming — payments not yet received and planned purchases / past) and bonds; an empty type or bond list means all, and choosing every type resets to all. `effectiveFilters` fits the saved filters to the wallet's bonds and currencies as the reports do (`fitScope` over `walletScopeOptions`, both next to `narrowWallet` in `entities`), except that a missing currency yields to the first one, so a saved filter never hides everything. `filterSchedule(wallet, filters)` narrows the wallet to the currency and bonds (`narrowWallet`), then keeps the types and the time picked; the payments screen picks only the year and the month. The chart and the totals show only the types let through. On the same day a payment sorts before a purchase (`compareScheduleEvents`).
- The bond picker (`/add`) is narrowed by currency and term to maturity and sorted by maturity or rate, chosen in the «Фільтри ОВДП» modal with a count per option; a line above the list names the filters in use. The list and the modal share them through `useBondPicker`. A chosen currency no longer in circulation yields to the first available one. ISIN search covers all bonds and ignores the filters.
- Navigation is native: the tab bar is `NativeTabs` (`expo-router/native-tabs`, the Liquid Glass bar on iOS 26, Material on Android). Native tabs draw no headers, so each tab is a group folder with its own stack (`(tabs)/(holdings)/_layout.tsx`, …), and screens pushed from a tab (bond, add, plan list) still open in the root stack over the tab bar. Every stack is `NativeStack` from `src/shared/ui/navigation/`, which owns the header options; don't set header colors per screen.
- Liquid Glass (`hasLiquidGlass` from `@/shared/lib`, iOS 26+): headers are transparent and the content scrolls under them, so scroll views keep `contentInsetAdjustmentBehavior="automatic"` and a non-scrolling element at the top is offset by `useHeaderHeight()`. Without glass (Android, older iOS) the header is a solid bar in `background`. Header buttons (`HeaderButton`) and the back button get glass from the system; the FAB is a tinted `GlassView` with a solid fallback. Glass belongs to the navigation layer and floating controls only, never to cards or other content.
- There are no top tabs: the payments tab is one year screen (upcoming payments are its «Майбутні» time filter), and the bond card (`/bond/[isin]`) is one scrolling screen.
- The plans tab shows the active plan; the header button opens «Мої плани» (`/plan/list`) to switch or create plans; it is the only way in.

## Persistence rules

- State is Zustand `persist` over MMKV via the synchronous adapter in `src/shared/lib/storage.ts`, so stores hydrate before the first render. Every store has the same layout: a folder named after it (`model/purchases/`, `model/plans/`, `model/activePlan/`, `api/bonds/`, `api/keyRate/`, `features/payment-filters/model/paymentFilters/`, `features/add-purchase/model/bondPickerFilters/`, `features/report-filters/model/reportFilters/`, `features/onboarding/model/onboarding/`, `shared/lib/toast/`, `shared/theme/themePreference/`) with `types.ts` (`<Name>State`), `store.ts` (`STORAGE_KEY`, exported `initialState`, and `use<Name>Store = create<<Name>State>()(persist(() => initialState, { name: STORAGE_KEY, storage }))`; only the toast store is not persisted), `selectors.ts` (`use…` hooks and `get…` getters), `actions.ts` (exported functions with explicit return types that change the state through `setState`; no setters inside the state) and `index.ts` (`export * from './actions'; export * from './selectors'; export type * from './types';`, never the raw store hook). Copy an existing store when adding one. The app is pre-release and installed on clean devices: stores have no `version`/`migrate` and nothing reads older data shapes or backup formats. A changed shape simply starts empty; users move data via backups.
- Storage keys are deliberately frozen: purchases live under `holdings-v1` (the state field is now `purchases`), plans under `investment-plan-v1`, payment filters under `payment-filters-v1`, bond picker filters under `bond-picker-filters-v1`, every report's filters under `report-filters-v1`, NBU cache under `nbu-bonds-v1`, NBU key rate under `nbu-key-rate-v1`, theme under `theme-preference-v1`, active plan under `active-plan-v1`, the seen onboarding under `onboarding-v1`. Don't rename them.
- No `__DEV__`-only code paths or dev fixtures in the app.
- Zod is used only for forms. NBU responses, stored state and backup contents are not validated: they are typed with TypeScript types and `as`/generics (`nbuClient.get<NbuSecurity[]>`, `JSON.parse(text) as T`). Don't add zod schemas or hand-written shape checks outside forms.
- Every wallet purchase belongs to a plan (`planId`); the app shows the active plan's purchases, and with no plans only the first-plan screen (`/welcome`, the plan-name screen) and backup import are reachable. The bond picker `/add` serves both the wallet and plans (`planId` param).
- Backup JSON (`src/features/backup/model/backup.ts`) is version 6 and always encrypted with a key the user types (twice on export): Argon2id derives the key, AES-256-GCM encrypts `{ holdings, plans }` (`src/features/backup/lib/backupCipher.ts`, `react-native-quick-crypto`); the file keeps `format`, `version`, `exportedAt`, the `encryption` parameters and base64 `data`. Only this version is read: `parseBackup(text, key)` checks `format` and `version`, decrypts (a wrong key throws `WrongBackupKeyError`), needs at least one plan and a plan in the file for every purchase. `backup.ts` stays the file codec; file actions are in `api/backupFile.ts`, and `restoreBackup` (`model/restoreBackup.ts`) reads the current plans and purchases, confirms if anything will be replaced and shows the toast. The key's form schema is `model/backupKey.schema.ts`. Restoring replaces all plans and purchases. A lost key cannot be recovered.
- The cloud copy is the same encrypted file, kept in Firebase: `@react-native-firebase/auth` signs in with Google through Firebase's web flow (`signInWithPopup` with `new OAuthProvider('google.com')`, as `new GoogleAuthProvider()` throws on the native SDKs; it returns by the plist's `REVERSED_CLIENT_ID` scheme, and closing it is `auth/popup-closed-by-user`), and Firestore `backups/{uid}` holds `{ email, exportedAt, backup }`, one copy per account, replaced on upload after a confirmation. Only `features/backup/api/` talks to Firebase (`googleAccount.ts`, `cloudBackup.ts`, `useCloudBackup.hook.ts`); security rules live in `firestore.rules` and are pasted into the console. The RNFirebase 27 auth plugin patches SceneDelegate so Firebase reads that return link (`…/firebaseauth/link`); it does so whenever `expo-router` is a plugin. The link still reaches Expo Router, so `src/app/+native-intent.ts` drops it (`redirectSystemPath` returns `null`) instead of showing «Unmatched Route». Removing the cloud data has Google confirm the account (`reauthenticateWithPopup`), then deletes the document and the Firebase user.
- Server requests go through TanStack Query hooks (`useBonds`, `useKeyRate` in `src/entities/portfolio/api/`): the hook fetches and saves each new answer into a persisted Zustand store in its `queryFn`, which the screens read. Stores never fetch. The catalog refetches when older than 6 hours (the current key rate 12), also when the app returns to the foreground; after a failure the next automatic try waits at least 5 minutes (`src/shared/api/queryClient.ts`). `useKeyRate(date)` takes the rate on a date (today's for a future date), stores it by date and never refetches a past date; `useKeyRates(dates)` does the same for many dates at once (the yield report's purchase dates), through the same query (`keyRateQuery`). The query client and `QueryProvider` live in `src/shared/api/`; a query with `meta.errorTitle` shows a toast with «Повторити» when it fails over data already shown. The cloud backup query (`useCloudBackup`) is the exception: it is read live and not cached in a store.
- Pull-to-refresh: give `RefreshControl` the state from `usePullToRefresh(refresh)` (`@/shared/lib`), never a background loading flag — otherwise the spinner shows whenever a screen opens and NBU data happens to refresh.
- Empty states: a screen, list or report with nothing to show renders `EmptyState` (`src/shared/ui/layout/`) with an icon, a title and a message saying why it is empty and what would show something (another year, other filters, the «Отримані» time…), never a bare line of text. `layout="screen"` (the default) fills a screen of its own; `layout="inline"` stands in a scrolling screen or a list (`ListEmptyComponent`) under what still shows there. When filters cause it, the icon is `funnel-outline` and the message points to them; it adds no button that repeats the header's filters button. An empty report's `EmptyState` is decoration.
- Feedback: events go to a toast — `showToast({ tone, title, message?, action? })` from `@/shared/lib` (store in `src/shared/lib/toast/`, `ToastHost` rendered once in `src/app/_layout.tsx`; it shows for 4 s, 6 s with an action, closes on tap, and a new toast replaces the last). Use it for a failed NBU refresh over cached data (with «Повторити») and finished actions. Confirmations stay `confirmDestructive` alerts; lasting states (no NBU data) stay inline.
- Forms use `react-hook-form` with `zodResolver` and `mode: 'onChange'`. The zod schema turns input text into values (`z.input` / `z.output` typing on `useForm`) and holds the user-facing messages; a form schema that depends on data is a factory next to its hook (`purchaseFormSchema(bond)`). Save is disabled while the form is invalid, and each field shows its error once edited: `FieldRow` (`src/shared/ui/form/`) under a row, or the `Section` footer under a block field. Read `isValid` / `errors` through `useFormState({ control })` and values through `useWatch` — not `form.formState`, which the React Compiler would cache.
- Screens with text fields scroll in `FormScrollView` (`src/shared/ui/layout/`, `KeyboardAwareScrollView` from `react-native-keyboard-controller` under the `KeyboardProvider` in `src/app/_layout.tsx`): it keeps the focused field and its error above the keyboard on iOS and Android. A screen whose content is a list that grows with the data is a `FlatList` / `SectionList` instead (the wallet, the bond picker, the payments, «Мої плани», the bond card, every report but the year-over-year one): what comes before the rows goes in `ListHeaderComponent`, what ends the screen in `ListFooterComponent`, the empty state in `ListEmptyComponent`, each row in a `SectionCell` so a section's rows read as one card; the content is `[screenContent, { gap: 0 }]` and headers and footers space themselves, render callbacks are named functions above the return. Report lists go through `ReportList` (`pages/reports/ui/`: a section per currency, `ReportSectionHeader` for its blocks, pull-to-refresh and the report's closing lines). Other screens use `ScreenScrollView`; filter screens, the reports list and the year-over-year report stay there, as their rows are few and of many kinds.
- Dates are `YYYY-MM-DD` strings everywhere (as NBU returns them) and are compared as strings. `date-fns` is used only in `src/shared/lib/date.ts`; put new date logic there, in local time.

## Styling conventions

- Every component has its own `StyleSheet.create((theme, rt) => …)` from `react-native-unistyles`; component states are `variants` + `styles.useVariants()`; safe-area insets come from `rt.insets`.
- No raw spacing, radius, shadow or color values in components: use `theme.space.*` (4-pt scale `xxs`…`xxxl`), `theme.radius.*`, `theme.shadowCard` / `theme.shadowRaised` and the palette (`src/shared/theme/tokens.ts`, `palette.ts`). Static styles outside the theme (`screenContent`, FAB offsets) import `space` directly. Rows and screen edges are `lg` sideways and `md` vertically; sections are `xl` apart. Sizes of controls (heights, icon boxes) may stay numbers.
- Shadows use `boxShadow` strings, never `shadow*`/`elevation`. Never put a shadow and `overflow: 'hidden'` on the same view: the outer view casts it, an inner one clips (see `Section`, `SectionCell`). In dark mode `shadowCard` is transparent; the lighter card surface separates cards.
- Palette roles: deep teal `accent` for actions and income, vermilion `fab` / `danger` / purchases for money going out. Signed result amounts use `SignedValue`: `success` green above zero, `danger` red below zero, `primary` neutral at zero; gross amounts without a sign stay neutral. Status colors for advice: `success` (green, all well), `warning` (amber, look before acting), `danger` (a loss, a mistake, an error); `*Surface` tints a banner of that status. Errors that block an action stay `danger`; a state that only needs attention (stale or missing NBU data) is `warning`. Text pairs pass WCAG AA; chart series were checked with the dataviz validator — re-run it when changing `series*` colors.
- Colors needed as non-style props (`tintColor`, `placeholderTextColor`) go through `withUnistyles`. `useUnistyles()` is reserved for navigator options in `src/app/`.
- The theme is chosen in settings: `src/shared/theme/themePreference/` applies it to Unistyles (`adaptiveThemes` for system, `setTheme` for an explicit one) and to `Appearance`, so native controls match; `unistyles.ts` reads the stored choice before `StyleSheet.configure`.
- `DateField` (`src/shared/ui/form/`) gets `themeVariant` and `accentColor` through `withUnistyles` on iOS. On Android the dialog takes its colors from the native theme added by the local plugin `plugins/withDatePickerAccent.js`: its `app.json` parameters repeat the palette's `accent` and header colors, so update them with `palette.ts` and rebuild.
- Icons are Ionicons from `@react-native-vector-icons/ionicons/static` (font embedded by its config plugin in `app.json`; not `@expo/vector-icons`, which Expo is deprecating). In components use `ThemedIcon` from `src/shared/ui/icon/` with `uniProps={(theme) => ({ color: … })}`; icon props are typed `IconName`. Tab bar icons are the exception: SF Symbols (`sf`) on iOS and Material Symbols (`md`) on Android in `NativeTabs.Trigger.Icon`, the SF Symbol filled when the tab is selected.
- Illustrations are drawn with React Native Skia (`@shopify/react-native-skia`): `IconBadge` (`src/shared/ui/icon/`, an Ionicons glyph on a lit disc in a breathing glow with a comet on its orbit; `EmptyState` takes its `icon`) and the onboarding backdrop (blurred patches of `accent` and the series colors that drift and follow the pager). Skia takes colors as props, so the drawing component gets them through `withUnistyles` + `uniProps`; motion runs off `useClock()` with Reanimated derived values and stands still under reduced motion. `withAlpha` (`@/shared/lib`) fades a palette color for gradients. The shared `LineChart` and `ColumnChart` draw their plots with Skia while native text keeps axes and labels accessible. `ColumnChart` accepts `orientation="vertical"` (default) or `"horizontal"`, with the same stacked series and signed baseline; `valueFormat="percent"` is available for rates. The line chart uses Gesture Handler, Reanimated and Worklets for point selection. A future PDF export must capture chart canvases as images before embedding them.
- Each currency has its own badge color (`currencyUah` berry, `currencyUsd` green, `currencyEur` indigo; `currencyColor(currency)` from `@/shared/theme`), used by the `Avatar` of the wallet's and the bond picker's rows; rows of a purchase or a payment (the schedule, the bond card's purchases, the bond and FX reports) badge it with `Avatar` in the event type's series `badge` color. A row that leads with such a badge takes `Avatar`, never a copy of it. `Avatar` takes any palette key that `accentText` reads on: the light label sits on these fills, on `accentFill` (the primary button, the selected segment) in both themes, each at 4.5:1 or more. The currencies were checked with the dataviz validator in both themes — re-run it when changing them.
- Chart series colors use `SeriesColor` keys (`coupon`, `redemption`, `purchase`) from `src/shared/theme/series.ts`, not color strings.
- One React component per `.tsx` file; shared types/utilities go in separate `.ts` files next to their consumers.
